# Architecture

## Executive summary

Use a Git-versioned OKF v0.2 bundle as the canonical knowledge layer. Each
knowledge item is a standalone UTF-8 Markdown file with explicit YAML
frontmatter, normal links, immutable identity, source lineage, lifecycle, and
trust signals. Humans can read and edit the files with basic tools; agents can
parse and propose changes without a proprietary SDK.

The design intentionally separates three layers:

1. **Canonical knowledge:** Markdown files, sources, indexes, and Git history.
2. **Deterministic governance:** a profile schema and corpus-level validation.
3. **Consumers:** inline CLI setup, Git-backed brain distribution, disposable
   keyword search, complete-item retrieval, and a coding-agent workflow skill
   are implemented consumers; MCP, APIs, graphs, native apps, and external
   platforms remain rebuildable from the canonical layer.

Baseline OKF conformance and local governance are different contracts. An OKF
consumer must be permissive. The local authoring gate can be stricter so that a
maintained organizational corpus does not accept missing identity, weak
provenance, broken curated links, or unsafe lifecycle transitions.

## Problem definition

Organizations accumulate decisions, procedures, concepts, system knowledge,
source material, and unresolved questions across tools. A normal document
collection does not reliably answer:

- Which item is the current one?
- Where did each claim come from?
- Was the item written by a human, imported, transformed, calculated, or
  generated by an agent?
- Who checked the current content and when?
- Is it still within its validity and freshness window?
- What does it supersede, conflict with, or depend on?
- Can the corpus move to a different tool without losing meaning?

The core system must answer those questions from files and history before any
retrieval or integration layer is introduced.

## Design principles

1. **Files are canonical.** Databases and indexes are disposable derived state.
2. **Readable without tooling.** Metadata cannot replace a clear title,
   summary, structured body, and citations.
3. **Explicit over implicit.** Type, identity, producer, lifecycle, and source
   lineage travel with the item.
4. **OKF vocabulary first.** Reuse upstream field names and actor conventions
   before introducing extensions.
5. **Stable identity, movable files.** A UUID persists when a path changes.
6. **Paths remain useful.** Readable filenames and ordinary Markdown links
   preserve baseline OKF and human navigation.
7. **Evidence is not truth.** Provenance and verification are signals; neither
   guarantees correctness.
8. **Confidence is not authority.** A highly confident agent is not an
   authorized policy owner.
9. **No silent replacement.** Material changes are reviewed; old knowledge is
   deprecated, superseded, or archived with history.
10. **Deterministic gates.** Syntax, referential integrity, dates, and state
    rules are code-checkable. Semantic conflict remains a human judgment aided
    by tools.
11. **Small taxonomy.** Add types only when their body contract or governance
    differs materially.
12. **Disposable consumers.** Retrieval, embeddings, graphs, and APIs must be
    reconstructable from the bundle.

## OKF compatibility assessment

Target: OKF v0.2, implemented against pinned upstream commit
`374e0bc4c644310ff56cdf9c0fe81eccdec862b0` after reinspection on 2026-08-12.

| Area | Upstream OKF v0.2 | `core-kb/0.1` profile | Compatibility |
|---|---|---|---|
| Bundle | Directory of Markdown concepts; optional reserved indexes/logs | Future bundle rooted at `knowledge/` | Compatible. |
| Required field | Only `type` | Requires additional governance fields | Every profile-valid concept is intended to be OKF-valid; not every OKF-valid concept is profile-valid. |
| Identity | Path without `.md` | Path plus immutable `urn:uuid:` `id` | `id` is an allowed extension. |
| Types | Open vocabulary | Seven initial lowercase values | A local authoring restriction; external OKF import must tolerate others. |
| Provenance | Optional `sources` | Conditional source requirement | Uses the upstream shape. |
| Producer | Optional `generated.by/at` | Required; adds `generated.method` | Compatible extension inside the upstream family. |
| Verification | Optional list or bare mapping | Canonical list form; human verification required for stable authoritative types | Consumers must accept the upstream bare mapping on import and normalize without losing meaning. |
| Lifecycle | `draft`, `stable`, `deprecated`; absent means stable | Field required; same values | Compatible and removes ambiguity. |
| Freshness | Optional absolute `stale_after` | Required for stable policy/procedure/system items | Compatible stricter profile. |
| Links | Normal Markdown; broken links tolerated | Same links; broken curated links are profile errors | Stricter quality policy, not an OKF conformance claim. |
| Extensions | Unknown keys allowed and preserved | Known fields plus namespaced `x-` keys | Authoring restriction; import/round-trip must remain lossless. |
| Archive | Not a status | Folder/disposition, normally after deprecation | Does not invent an incompatible status. |
| Attestation | Optional `Attested Computation` type | Deferred | No conflict. |

The root `knowledge/index.md` should declare `okf_version: "0.2"`. The exact
syntax must follow the current upstream spec when Phase 1 starts. Pinning the
upstream commit prevents a mutable `main` branch from changing acceptance
criteria during implementation.

## Recommended directory structure

```text
knowledge/
├── index.md                  # root progressive index + OKF version
├── log.md                    # high-level chronological changes
├── inbox/                    # draft candidates, not arbitrary scratch files
├── curated/
│   └── concepts/             # reusable explanatory knowledge
├── projects/                 # project-scoped navigation; type remains in files
├── systems/                  # systems and technical architecture
├── procedures/               # procedures and runbooks
├── decisions/                # decision records
├── policies/                 # normative organizational rules
├── sources/                  # source-summary concepts
├── questions/                # unresolved, owned questions
├── notes/
│   └── daily/                # temporary notes; usually draft and short-lived
├── references/               # mirrored external artifacts where lawful
└── archive/                  # deprecated or abandoned material retained for history
```

Every directory may have an `index.md` and, where useful, a `log.md`. Index
entries show title and description and link one level down. They are navigation
artifacts, not duplicate metadata stores.

### Folder-based versus metadata-and-link organization

Folders provide low-cost browsing, ownership cues, progressive disclosure, and
reasonable Git diffs. They are poor canonical semantics because paths change,
an item may relate to several domains, and folder taxonomies become deep.

Metadata and links support cross-cutting filtering and graph traversal. They
can become burdensome if every relationship is typed or if tags substitute for
clear prose.

Use a hybrid:

- a shallow, stable folder structure for dominant workflow/context;
- `type`, `status`, and immutable `id` for document semantics;
- normal Markdown links for understandable relationships;
- only `related`, `supersedes`, and `superseded_by` as typed ID relations in
  v0.1; and
- tags for cross-cutting discovery, never for lifecycle or authority.

A file move must preserve `id`, `type`, creation time, and provenance. It must
update affected Markdown paths and indexes in the same change.

## Knowledge model overview

The minimal item contract is defined in [schema.md](schema.md). Conceptually:

```text
Knowledge item
├── identity: id, type, title, description
├── lifecycle: status, created_at, updated_at, valid_from, stale_after
├── production: generated { by, at, method }
├── evidence: sources[], verified[], confidence
├── relationships: related[], supersedes[], superseded_by[]
├── handling: tags, sensitivity, archived
└── content: structured Markdown body with ordinary links and citations
```

The frontmatter is deliberately not a complete knowledge graph. It holds
stable, queryable governance facts. The body holds explanation, context,
evidence, and the words that make relationships understandable.

## Provenance and trust architecture

### Provenance classes

| Class | Representation | Minimum evidence |
|---|---|---|
| Original human-authored | `generated.method: human-authored`, `generated.by: human:<id>` | Actor, timestamp, Git commit; sources optional unless factual claims derive from material. |
| Imported external material | `method: imported` | At least one source with resolvable resource; item stays draft until curation. |
| Summarized/transformed | `method: transformed`, normally `type: source-summary` | All material sources; claim-level citations for consequential assertions. |
| Agent-generated suggestion | `method: agent-generated`, non-human producer | Sources, confidence with basis, draft by default; human verification before authoritative use. |
| Human-verified | `verified` contains `human:<id>` for current content | Verifier and timestamp; verification scope described in the body/review record. |
| Derived calculation | `method: calculated` | Input sources and documented formula/method; formal OKF attestation deferred. |
| Deprecated/superseded | `status: deprecated`, optional reciprocal supersession IDs | Reason/current replacement in body; preserved Git history. |

### Source conflict ranking

An agent may propose an ordering but must expose the evidence and never silently
resolve a consequential conflict. Evaluate in this sequence:

1. **Applicability:** scope, jurisdiction, system/version, and effective date.
2. **Lifecycle:** current beats deprecated; non-stale beats stale, all else
   equal.
3. **Authority:** policy owner, decision owner, canonical resource, or primary
   evidence beats an unattributed restatement.
4. **Verification:** current human review beats machine-only confirmation;
   independence and review scope matter.
5. **Directness:** original record/data beats a summary; a summary can aid
   comprehension but not outrank its source.
6. **Corroboration:** multiple genuinely independent sources strengthen a
   claim; copies of one source do not.
7. **Uncertainty:** confidence communicates uncertainty but cannot confer
   authority.

If two applicable, current, authoritative sources disagree, keep both and
create a `question` or `decision` that identifies the conflict, owners, impact,
and required resolution. Consumers should warn rather than synthesize a
fictional consensus.

### Freshness

Freshness is multi-dimensional:

- `sources[].last_modified`: when a source changed;
- `generated.at` / `updated_at`: when current prose materially changed;
- latest `verified[].at`: when someone or a process checked it; and
- `stale_after`: deterministic review deadline.

A recently rewritten summary of an old policy is not fresh policy. A stale
item is not automatically false; it is ineligible for unattended authoritative
use until reviewed. Stable policy, procedure, and system items require a
`stale_after` date in the proposed profile.

### Confidence versus authority

`confidence` is the producer’s stated uncertainty about the current claim,
with a plain-language basis. Authority comes from role, ownership, source,
applicability, and approval. Verification records that a check occurred. These
dimensions must remain separate.

Examples:

- An agent may have `high` confidence in a plausible but unauthorized policy:
  high uncertainty confidence, zero policy authority.
- A signed policy can be authoritative but stale: strong authority, poor
  freshness.
- A nightly process can confirm a metric mechanically: machine-confirmed, not
  human-reviewed.

### Human approval boundaries

Human approval is required before:

- an agent-generated item becomes stable when it is authoritative or used for
  operational action;
- a decision, procedure, or policy becomes stable;
- current stable authoritative knowledge is materially changed;
- supersession or deprecation changes what consumers should treat as current;
- conflicting authoritative sources are resolved;
- sensitive content is lowered in classification or published outside its
  existing boundary; or
- a derived calculation is represented as approved organizational truth.

Agents may capture, normalize, summarize, link, check syntax, flag duplicates,
calculate candidate staleness, and prepare diffs. They may not claim a human
actor, fabricate sources or verification, or infer approval from a merge alone
unless governance explicitly defines the merge as approval.

## Versioning and audit strategy

Git is the audit substrate, not frontmatter duplication of a change log.

- One logical knowledge change per commit where practical.
- Pull requests show content, metadata, link, and lifecycle changes together.
- Rename detection preserves path history while immutable `id` preserves
  corpus identity.
- Signed commits/tags may be added later but are not required in the first
  milestone.
- Current frontmatter describes current content. Old verification and old
  metadata remain discoverable in Git history.
- `log.md` records notable human-facing changes, not every mechanical edit.
- Never rewrite published history as a normal lifecycle operation.
- Source snapshots, when lawful and necessary, should be content-addressed or
  otherwise tied to an immutable revision; URLs alone may change.

Auditability still depends on repository governance. Git history can be
rewritten, actor strings can be forged, and timestamps can be wrong. These are
signals, not cryptographic guarantees.

## Security and privacy considerations

The core file model has no authorization. A `sensitivity` label is descriptive
and cannot prevent access. Therefore:

- do not store credentials, tokens, private keys, or secrets in the bundle;
- assume every Git clone receives every committed object, including deleted
  history;
- separate restricted knowledge into a separately controlled repository or
  bundle rather than relying on folders or tags;
- minimize personal data and avoid `person` items in the first taxonomy;
- use stable non-secret actor identifiers; avoid unnecessary emails where an
  internal opaque ID suffices;
- review imported source licensing and retention rights before mirroring it;
- treat prompt injection or hostile instructions in imported material as
  untrusted content, not agent commands;
- prevent agents from changing `sensitivity`, source evidence, or human
  verification without explicit review;
- redact before commit; removal from the latest tree is not removal from Git
  history; and
- run validators offline by default so validation does not leak content.

Any later retrieval or connector layer must enforce source permissions. This
phase does not design that layer.

## Risks and tradeoffs

| Choice | Benefit | Cost / mitigation |
|---|---|---|
| Markdown + YAML | Portable, inspectable, diffable | YAML edge cases; use YAML 1.2 safe parsing, ban custom tags/aliases, and format deterministically. |
| Immutable UUID | Survives moves and merges | Hard to type; templates/tools generate it and filenames stay readable. |
| Strict local schema | Consistency and reliable automation | Narrower than OKF; distinguish profile errors from OKF conformance and preserve unknown import data. |
| Duplicate path and UUID identity | Compatibility plus durability | Two identifiers can diverge; validator enforces UUID uniqueness and treats path as an alias. |
| Explicit timestamps | Portable audit hints | Manual drift; validator compares dates, while Git remains the audit source. |
| Human verification gates | Prevents authority laundering | Review bottleneck; limit gates to authoritative/high-impact content. |
| Typed supersession metadata | Currentness is machine-checkable | Reciprocal fields can drift; validate both ends atomically. |
| Shallow folders | Easy navigation | Imperfect classification; links and metadata handle cross-cutting meaning. |
| `additionalProperties: false` with `x-` escape | Catches typos | Extension friction; approve and namespace extensions deliberately. |
| No database | Maximum portability | Corpus-wide checks require scanning files; acceptable for first milestone. |

## Final design review

| Criterion | Assessment |
|---|---|
| Current OKF compatibility | Targets v0.2 names, status values, actors, links, indexes, and logs; extensions are permitted. |
| Human usability | Plain files, readable names, one-sentence descriptions, predictable body sections. |
| Agent usability | Deterministic frontmatter, stable IDs, explicit states, citations, and proposed schema. |
| Portability | UTF-8, CommonMark-compatible Markdown, YAML 1.2, relative/bundle links, no runtime dependency. |
| Git friendliness | Small text files, stable formatting, no generated binary state, explicit move rules. |
| Extensibility | Namespaced extensions, open Markdown body, stable future consumer boundary. |
| Provenance quality | Conditional source requirements, claim citations, actors, method, verification, Git history. |
| Stale/conflict resistance | Absolute stale dates, effective dates, supersession, conflict workflow, no semantic authority shortcut. |
| Search | QMD BM25 indexes Markdown as disposable state; results are remapped to item/brain IDs, paths, lifecycle metadata, and pinned commits. |
| Future CLI/MCP | Operations can wrap deterministic file transitions; core model does not depend on those interfaces. |

## Deferred capabilities

The CLI consumer phase has started without changing the canonical model.
QMD BM25 indexing and cited keyword queries are implemented as isolated,
deletable consumer state. Detailed implementation is still deferred for model
installation, semantic/hybrid retrieval, embeddings, vector databases, graph
databases, lifecycle CLI commands, MCP, APIs, web/native UI, hosted services,
authentication, authorization, multitenancy, background agents, production
infrastructure, and third-party connectors. See [cli.md](cli.md) for the active
consumer boundary.
